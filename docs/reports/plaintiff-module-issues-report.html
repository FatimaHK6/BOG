A. Frontend Issues 22 issues

Issues found in Angular components, services, and templates

FE-01 requestId defaults to 0 — FK constraint violation on save Critical Bug

plaintiff-form.component.ts:31

requestId: number = 0 — When the requestId query parameter is missing or invalid, the form sends CaseRegistrationRequestId = 0 to the backend, which does not exist in the database.

The POST call goes to /api/case-requests/0/plaintiffs causing a SQL FK constraint violation. The user sees "حدث خطأ أثناء إنشاء المدعي".

Impact: Plaintiff creation completely broken when requestId is not in the URL.
FE-02 Address validation over-restriction — all 8 fields required instead of 2 (BC04) Critical SRS Non-Compliance

plaintiff-form.component.ts:625-919 (all type cases)

Per SRS BC04, only regionId and cityId are mandatory in the national address model. However, the implementation sets Validators.required on ALL 8 address fields (district, street, building, unit, postal, additional code) for every plaintiff type.

Affected types: 1, 2, 3, 4, 7, 8 — every type with an address section.

Impact: Users cannot save a plaintiff without filling ALL address fields, even though SRS only requires region + city. This blocks form submission.
FE-03 Type 1: Profession field not validated as required Critical SRS Non-Compliance

plaintiff-form.component.ts:537

SRS Section 2.5 specifies Profession (المهنة) as mandatory for Type 1 individuals ("المهنة - نص - نعم"). However, no Validators.required is set for the profession field in updateFormValidation() for Type 1. It's only conditionally set through BC01 logic.

Impact: Type 1 plaintiff can be saved without profession, violating SRS requirement.
FE-04 Race condition in loadAllRepresentatives() High Bug

plaintiff-list.component.ts:367-409

Uses a completedRequests counter in a closure with concurrent API subscriptions. If API call order differs from forEach order, state corruption can occur. Multiple subscriptions fire independently with no synchronization.

Impact: Representatives may not load correctly or display for the wrong plaintiff.
FE-05 BR08: Absher verification not enforced at save time High SRS Non-Compliance

plaintiff-form.component.ts:1559

SRS BR08 requires Absher verification for Type 1 individuals before saving. The UI shows a warning indicator but the form's onSave() method does not check isAbsherVerified. Absher can be bypassed entirely.

Impact: Individual plaintiffs can be created without Absher verification, violating BR08.
FE-06 Absher readonly fields can be modified programmatically High Security

plaintiff-form.component.html:85-161

Absher-fetched fields use [readonly]="isAbsherFieldsReadonly()" HTML attribute, but the form controls remain enabled. Values can be changed via browser DevTools or form.patchValue(). Should use formControl.disable() instead.

Impact: Absher-verified data (name, birth date, identity) can be tampered with.
FE-07 Representative type restrictions not enforced on backend High SRS Non-Compliance

representative-dialog.component.ts (ALLOWED_REPRESENTATIVE_TYPES)

Each plaintiff type allows specific representative types (e.g., Type 5 only allows وكيل). The frontend filters the menu correctly, but there is no server-side validation. A crafted POST request can bypass the frontend restriction.

Impact: Invalid representative types can be saved for a plaintiff by bypassing the UI.
FE-08 Attachment type restrictions not enforced per plaintiff type (BC01) High SRS Non-Compliance

plaintiff-form.component.html:1482-1486

SRS BC01 states each plaintiff type has specific allowed attachment types. The current implementation accepts any attachment type for any plaintiff type. No mapping of plaintiff type → allowed attachment types exists.

Impact: Wrong attachment types can be uploaded for any plaintiff type.
FE-09 Demo data fallback without user warning Medium UX

plaintiff-list.component.ts:156

When the API call fails, loadDemoData() is called silently. Users see fake/demo data without any indication it's not real. No error message or banner shown.

Impact: Users may make decisions based on demo data thinking it's real.
FE-10 Temporary attachment IDs use Date.now() — collision risk Medium Bug

Temporary attachment IDs are generated with Date.now(). Two rapid uploads within the same millisecond get the same ID, causing deletion of the wrong attachment.

Impact: Rapid file uploads may collide, causing wrong file to be deleted.

BE-01 PlaintiffAttachmentCreateDTO missing FileSizeBytes & validation Critical Data Integrity

BOG.DTO/Plaintiff/PlaintiffAttachmentDTO.cs:1-42

The DTO accepts FileContent (Base64) but has no FileSizeBytes field. The entity requires it. No FluentValidation validator exists for this DTO. The controller comment mentions "PDF only, max 4MB (BR04)" but no actual validation exists in code.

  • No file size limit validation (4MB per BR04)
  • No Base64 validity check
  • No PDF magic bytes verification
Impact: Any file type/size accepted; no BR04 enforcement. DB may reject missing FileSizeBytes.
BE-02 Representative attachment file storage not implemented Critical Incomplete Implementation

BOG.BL/Services/PlaintiffBL.cs:459-464

A TODO comment indicates file content handling is not implemented: "TODO: Save file content to storage if FileContent is provided". Attachment metadata records are created in the database, but actual file bytes are never stored anywhere.

Impact: Representative attachments appear to upload successfully but files are permanently lost.
BE-03 Orphaned address records on plaintiff save failure High Data Integrity

BOG.BL/Services/PlaintiffBL.cs:123-184, 269-270

Address records are created with separate SaveChangesAsync() calls (one per address type). If one address succeeds but the plaintiff save at line 270 fails, orphaned Address records remain in the database with no parent reference. No transaction scope wraps the entire operation.

Impact: Database accumulates orphaned address records over time.
BE-04 Representative creation with potentially invalid PlaintiffId High Data Integrity

BOG.BL/Services/PlaintiffBL.cs:364-437

Representative entities use PlaintiffId = plaintiff.Id (line 366). If the plaintiff save fails at line 270, plaintiff.Id would be 0, causing FK constraint violations when representatives are saved at lines 470-473.

Impact: FK constraint error cascade when plaintiff creation fails.
BE-05 No FK validation for lookup table references Medium Data Integrity

BOG.BL/Services/PlaintiffBL.cs:207-267

Plaintiff entity is created with optional FK references (GovernmentAgencyId, CountryId, NationalityId, LicenseSourceId) but none are validated to exist in their lookup tables before save. Database constraints catch this, but error messages are cryptic.

Impact: Cryptic SQL errors instead of user-friendly validation messages.
